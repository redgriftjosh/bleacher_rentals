## Corrected finding — there is no permissions hole

The plan first claimed a viewer could create, edit and delete contacts. **That
was wrong**, and running the tests is what proved it.

The claim came from reading only the client-side write helpers
(`createContact`, `updateContact`, `softDeleteContact` and the company
equivalents), none of which checks a role. But those run against the local
PowerSync database. The upload then reaches Postgres, where row-level security
decides:

```
contacts_select  →  admin, account_manager, viewer
contacts_insert  →  admin, account_manager
contacts_update  →  admin, account_manager
```

A viewer's write is rejected at the database. The permission is enforced, and at
the right layer — a client-side check alone would be bypassable anyway.

What remains is a **UX problem, not a security one**: the page still offers "New
Contact", "Edit" and "Delete" to a viewer. PowerSync writes locally and shows
success, then the server rejects the upload and the change quietly disappears.
Worth hiding those controls for viewers, but nothing is exposed.

      rejects the write, but the UI lets them try and appears to succeed first

## Run notes — 2026-08-26

Tests 1, 2, 3 and 5 were written and run. Videos are in `test-results/`
(gitignored), one per test.

**Tests 1 and 2 pass.** They were rewritten twice before they meant anything.

The first version asserted that buttons were _absent_. That was weak: hiding a
button later would turn such a test green while the write path stayed open, and
the recording showed nothing but a page load. The tests now have the viewer fill
the form, save, and change a language — then read Postgres to see whether it
landed. The database is the judge, not the toast.

Rewriting them is what overturned the finding above.

**Test 2 first passed for the wrong reason.** Its locator looked for a button,
but contact rows are clickable `<tr>` elements, so it never opened the modal and
found no Edit button because nothing was on screen. A test that passes without
exercising anything is worse than no test.

**A second rewrite was needed** because `getByLabel` matches nothing on these
forms — see the accessibility item in the human list.

**Seeding a contact then looking for it in the list does not work** for a
permission test: a row inserted straight into Postgres has to travel through
PowerSync first, so the test would be waiting on sync, not on permissions. It now
uses a contact already on screen.

**Test 3 first failed on `net::ERR_ABORTED`**, which is the client-side redirect
interrupting the navigation — a refusal, not a defect. The test now swallows that
and judges on where the browser ended up.

**Test 4 was not written.** The ⌘/Ctrl+click shortcut lives on the PixiJS canvas
grid, where cells are drawn, not DOM elements — there is nothing for Playwright
to address. Its access rules are already covered by
`createWorkTrackerDraft.test.ts` (145 lines of unit tests over the same pure
function both entry points call). An e2e here would be slow and brittle for no
extra coverage. Worth revisiting only if the shortcut's behaviour diverges from
that function.
