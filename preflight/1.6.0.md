## Corrected finding — there is no permissions hole

An earlier draft of this plan claimed a viewer could create, edit and delete
contacts. **That was wrong**, and running tests 1 and 2 is what proved it.

The claim came from reading only the client-side write helpers (`createContact`,
`updateContact`, `softDeleteContact` and the company equivalents), none of which
checks a role. Those run against the local PowerSync database. The upload then
reaches Postgres, where row-level security decides:

```
contacts_select  →  admin, account_manager, viewer
contacts_insert  →  admin, account_manager
contacts_update  →  admin, account_manager
```

A viewer's write is rejected at the database — the layer where it cannot be
bypassed. The permission holds.

What remains is a **UX problem, not a security one**: the page still offers "New
Contact", "Edit" and "Delete" to a viewer. `createContact` writes locally and
calls `createSuccessToast` immediately, so the row appears and the user is told
it worked; the server then rejects the upload and it quietly vanishes. Recorded
on video during the run. Worth fixing, but nothing is exposed.

## Test 4 is not written

The ⌘/Ctrl+click shortcut lives on the PixiJS canvas grid, where cells are drawn
rather than being DOM elements — there is nothing for Playwright to address. Its
access rules are already covered by `createWorkTrackerDraft.test.ts`, 145 lines
of unit tests over the same pure function both entry points call. An e2e here
would be slow and brittle for no extra coverage. Revisit only if the shortcut's
behaviour diverges from that function.

### Tests 13, 14 and 15 were already covered

`supabase/tests/actual_bleacher.test.sql` covers the bleacher swap at the
database level with seven scenarios, including the exact recipient rule test 14
was written for: the work tracker's creator is notified once, on the NULL → value
transition only, and never the driver or a manager correcting their own edit. All
16 SQL test files pass, and CI already runs them.

This is better than an e2e would have been. Drivers have no web access at all —
the mobile app is a separate codebase — so 13 and 15 were never reachable from
Playwright.

### Tests 6 and 7 did not complete

Test 6 times out clicking the Quote Language dropdown inside the New Contact
modal. Isolated debugging shows the element present, visible, unobstructed and
clickable at that exact point, under the same viewport and config — so the fault
is in how the spec drives it, not in the page. Test 7 then fails because it looks
for the contact test 6 never created.

Left unfinished on purpose rather than chased further. The underlying behaviour
is covered elsewhere: `createContact.test.ts` and `updateContact.test.ts` assert
that the language is persisted and defaults to English, and the field was
exercised by hand earlier in this session.

### A collision that produced a false accusation

Tests 2 and 7 both selected "the first row" of the contacts table, which is
sorted by first name, and ran in parallel under different projects. The admin
spec changed the language of the very contact the viewer spec was measuring, and
the viewer was blamed for it — the run reported `a viewer changed the quote
language`.

That would have overturned the RLS finding for a second time, wrongly. Both specs
now address contacts they own, and preflight runs use `--workers=1`: tests that
mutate shared rows must not run concurrently.
